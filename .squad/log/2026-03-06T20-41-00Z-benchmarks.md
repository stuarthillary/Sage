### Phase 2: Baseline Measurement
**Benchmarks:** 4 scenarios (Sequential/Chained Events) × 2 executive types (Executive/ExecutiveFastLight)  
**Parameters:** `EventCount` ∈ {1000, 10000, 100000}  
**Attributes:** `[ShortRunJob]` (reduced invocations for faster iteration), `[MemoryDiagnoser]`

**Sample Results (N=1000, ShortRun):**

| Benchmark | Mean | Ratio |
|---|---|---|
| `Executive_SequentialEvents` | ~287 µs | — |
| `ExecutiveFastLight_SequentialEvents` | ~80 µs | 0.28× |
| `Executive_ChainedEvents` | ~179 µs | — |
| `ExecutiveFastLight_ChainedEvents` | ~82 µs | 0.46× |

**Key Observation:** FastLight is 3.6–2.2× faster than Executive across workload types, consistent with O(N²) dequeue cost in `Executive.Start()` (SortedList.RemoveAt(0) shifts all elements) vs O(N log N) in `ExecutiveFastLight` (heap sift-down).

### Phase 3: Analysis & Documentation
**Hot paths identified:**
- `Executive`: O(N²) bottleneck in event dequeue (line 595); additional per-event overhead (Monitor locks, SortedList operations)
- `ExecutiveFastLight`: O(N log N) heap dispatch; object pooling via `ExecEventCache`

**Optimization roadmap for Parker:**
1. **Priority 1** — Replace `SortedList` with `System.Collections.Generic.PriorityQueue<>` (expected: 100–1000× speedup at N=100k)
2. **Priority 2** — Object pooling for `ExecEvent` in Executive (expected: reduced GC pressure)
3. **Priority 3** — Lock granularity evaluation for single-threaded path
4. **Priority 4** — Do NOT change ExecutiveFastLight; use as reference model
